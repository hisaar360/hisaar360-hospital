1. WHAT THE PRODUCT DOES
================================================================================

Hospital Management System for a company that may own one or more hospitals.

TWO product editions (from hospital/company subscriptionPlan):

  A) HOSPITAL (default)
     Full HMS: OPD, doctors, appointments, prescriptions, patients,
     room/ward admission, laboratory, pharmacy POS, billing/ledger,
     users/roles, dashboard, audit logs.

  B) LABORATORY (lab / lab-only / pathology)
     Lab-only UI + permission set: patients, lab catalog, lab orders,
     results, users/roles, hospitals, settings. Dashboard, pharmacy,
     ward, appointments, prescriptions are hidden.

Core clinical idea:
  Patient is the master record.
  A visit/admission is an Encounter (OPD / admission / emergency / follow_up).
  Where a service is performed, a ledger charge is created.
  Payments are collected separately by receptionist / cashier / accountant.

Pharmacy inside HMS is the hospital pharmacy (POS + inventory), not a
standalone RMS shop. It still uses POS-style collections (products, sales,
inventory, register sessions) scoped by companyId.

3. HIGH-LEVEL REQUEST FLOW
================================================================================

  Browser (Angular SPA)
       │  Hosted login at www.hisaar360.com  OR  /login/access?ssoCode=
       │  Bearer JWT stored as localStorage "token"
       ▼
  GET/POST/PATCH/DELETE  /api/v1/<resource>
       │
       ▼
  Express:
       helmet → cors → json → requestLogger
       authMiddleware (JWT + HmsUserProfile/User + subscription + edition)
       requirePermission / requireAnyPermission
       hospital-scope (hospitalId from user, unless wildcard superAdmin)
       │
       ▼
  Controller → Service → Mongoose model
       │
       ▼
  JSON envelope { data, message } → Angular page


SSO login path:
  Central Auth issues a one-time ssoCode
    → POST /api/v1/auth/sso-login { code }
    → HMS verifies product (HSPTL0012 / hsptl-hisaar-3299498 / backend URL)
    → hydrates/creates HmsUserProfile + company + hospital roles
    → returns access + refresh tokens

Local login still exists (POST /auth/login) for leftover User collection
accounts, but hosted login is the default in production.

6. CORE DOMAIN MODEL (CURRENT)
================================================================================

COMPANY
  Tenant. Users, roles, pharmacy stock, and hospitals belong to a company.
  Central Auth company is mirrored locally.

HOSPITAL
  One clinical site under a company. Almost all clinical docs have hospitalId.
  Fields include subscriptionPlan (drives product edition), lab report
  settings, prescription settings.
  Super admin (wildcard *) can see all hospitals; everyone else is scoped
  to req.user.hospitalId.

DEPARTMENT
  Hospital department (Cardiology, Gynae, …). Doctors and appointments link here.

DOCTOR (DoctorProfile)
  Clinical doctor profile. May be created with a new login (name/email/password)
  or linked to an existing userId.
  Has consultationFee, availableDays/slots, prescription template settings.
  Role name "Doctor" is special: hospital-scope limits data to assigned patients
  and own appointments (assertDoctorPatientAccess).

PATIENT
  Master person record. patientNo is hospital-unique uppercase code.
  assignedDoctorId, demographics, allergies, chronic diseases, medications.
  Profile APIs: /patients/:id/profile, /history, /prescriptions, /bills.

PATIENT HISTORY
  Free-text clinical notes (diagnosis, vitals, attachments).
  Also used as the permission gate for ward UI and some lab screens
  (patients_history.read / create).

APPOINTMENT
  OPD booking: patient + doctor + department + date/time + status.
  Calendar: GET /appointments/calendar
  Status updates: PATCH /appointments/:id/status
  Completing a visit can open an OPD encounter (from-appointment).

PRESCRIPTION
  Doctor Rx: medicines[], advice, followUpDate, specialty print layouts
  (including gynae / physiotherapy). Doctor medicine shortcuts:
  GET/POST /prescriptions/doctor-medicines
  Pharmacy role can READ prescriptions (dispense from POS), not write them.

ENCOUNTER  (billing account for one visit/admission)
  Collection: encounters
  Types: opd | admission | emergency | follow_up
  Statuses: open | admitted | ready_for_discharge | discharged | closed | cancelled
  Numbers: ADM-YYYYMMDD-001, OPD-… (daily hospital document numbers)
  Links: patientId, appointmentId, roomAllotmentId, prescriptionId,
         consultantDoctorId, roomId, ward/bed labels
  summary: totalCharges, totalDiscount, netPayable, totalPaid,
           totalRefunded, balance  (recalculated on every item/payment change)

LEDGER ITEM  (ledger_items)
  One charge line. sourceType: pharmacy | lab | ward | doctor | manual |
  bed | procedure | nursing | misc | appointment
  Status: active | cancelled | refunded
  Unique-ish by hospitalId + sourceType + sourceId (lab order, bed stay, …)

LEDGER PAYMENT  (ledger_payments)
  advance | partial | final | refund
  Methods: cash, card, bank, online, wallet, check, jazzcash, easypaisa

CHARGE CATALOG  (charge_catalog)
  Master list of optional/manual charges for cashier (admission, drip,
  injection, oxygen, procedure, file, service, …)

BILL  (legacy collection `bills`)
  Still used. Lab orders still upsert a Bill with sourceType=lab.
  New clinical charges should go to the encounter ledger.
  UI Payments/Invoices pages still talk to both bills + encounters.

ROOM
  Physical room. roomType, chargesPerDay, optional wardId + floorId.
  Status: available / occupied / etc.

HOSPITAL WARD + WARD FLOOR
  Master structure for bed management UI.
  /hospital-wards  CRUD wards
  /hospital-wards/:wardId/floors  floors

ROOM ALLOTMENT
  Admission: patient assigned to a room/bed.
  Create → opens Encounter type=admission, status=admitted
  Discharge → auto bed charges (days × chargesPerDay), encounter discharged
  Transfer room, assign nurse also exist.

WARD runtime (/ward)
  beds, activities, admissions, vitals, MAR record-dose, drip actions,
  orders (can create lab orders), reports.
  Frontend ward modules: admissions, nursing-care, mar, drips-iv, vitals,
  io-chart, orders-services, shift-handover, inventory, reports.

LABORATORY
  LabTest catalog, LabOrder with items/samples/results.
  Flow: create order → collect sample → enter results → verify
        → optional reject sample / cancel item / upload report
  Settings live on Hospital (laboratorySettings) via /laboratory/settings
  Creating/updating an order:
    - upserts a legacy Bill (sourceType=lab)
    - finds or creates an Encounter and posts a ledger_item sourceType=lab
  Patient comparison / history:
    GET /laboratory/patients/:patientId/comparison
    GET /laboratory/patients/:patientId/history

PHARMACY (POS collections, hospital-scoped company)
  Categories, products, customers, suppliers
  Inventory + stock_movements (stock never stored on product)
  Stores / warehouses
  Sales (incl. held carts, convert-to-sale, invoice)
  Sales returns, transfers, payments, expenses
  Register sessions (open/close cash drawer)
  Pharmacy POS in mooli requires ALL of:
    sales.create, sales.read, products.read,
    register_sessions.open, register_sessions.read, register_sessions.close
  Pharmacy sales do NOT currently auto-post to the encounter ledger
  (docs list it as a next integration). Cashier can add manual ledger
  items with sourceType=pharmacy if needed.

USER vs HMS USER PROFILE
  User            — legacy local-login accounts
  HmsUserProfile  — Central Auth operators (centralUserId, companyId, roleId,
                    hospitalId, branch/warehouse access)
  Auth middleware looks up profile first, then User.
  JWT userId is the profile _id (or legacy user _id).

ROLE
  context: 'hospital'. System templates are upserted per company.
  Wildcard permission '*' = superAdmin (cross-hospital).

7. BUSINESS FLOWS (HOW USERS WORK)
================================================================================

--- 7.1 Master data first ------------------------------------------------------

  1. Company exists (Central Auth / register-business / seed)
  2. Create Hospital
  3. Create Departments
  4. Create Doctors (optionally with login)
  5. Create Roles (auto-seeded templates) and Users
  6. Create Rooms / Hospital Wards / Floors / Ward beds
  7. Optional: Lab test catalog (or POST /laboratory/tests/seed-defaults)
  8. Optional pharmacy: store, warehouse, categories, products, opening stock

--- 7.2 OPD visit --------------------------------------------------------------

  1. Reception: create/find Patient
  2. Book Appointment (patient + doctor + slot)
  3. Doctor: see Doctor Dashboard, open appointment, write clinical notes
     (patient-history) and Prescription
  4. POST /encounters/from-appointment
       → Encounter type=opd
       → consultation fee ledger item if appointment.consultationFee > 0
  5. Cashier: Payments → patient ledger → collect payment

Landing after login for Receptionist: /appointments
Landing for Doctor: /doctor-dashboard

--- 7.3 Inpatient admission ----------------------------------------------------

  1. Room Allotment create (patient + room)
       → Encounter type=admission, status=admitted
       → optional advance payment on ledger
  2. Ward Admin / Nurse: bed board, vitals, MAR, drips, I/O, handover
  3. Lab orders / pharmacy issues during stay (lab auto-posts to ledger)
  4. Discharge:
       PATCH /room-allotments/:id/discharge
         OR GET /encounters/:id/discharge-preview
            POST /encounters/:id/finalize-discharge
       → bed charges (days × room.chargesPerDay)
       → encounter status = discharged

Landing for Ward Admin / Nurse: /ward/dashboard

--- 7.4 Laboratory -------------------------------------------------------------

  1. Create/select Patient
  2. Lab Dashboard → Create Order (pick tests from catalog)
  3. Collect sample → enter results → verify (lab_results.verify)
  4. Print report (hospital laboratorySettings colors/header)
  5. Order amount is billed:
       Bill sourceType=lab  AND  ledger_item sourceType=lab on an encounter
  Laboratory edition: home route is /laboratory; other clinical menus hidden.

--- 7.5 Prescription -----------------------------------------------------------

  Doctor (or Hospital Admin) creates Rx on /prescriptions
  Print templates vary by specialty (gynae, physiotherapy plan, clinical Rx)
  Pharmacy users can read Rx to dispense; they cannot create Rx.

--- 7.6 Billing / cashier ------------------------------------------------------

  Screens:
    /payments                 patient payment summaries
    /payments/ledger          encounter ledger UI
    /payments/invoices        invoice list
    /payments/addpayment      add payment / charge
  APIs:
    GET  /encounters/patient-payments
    GET  /encounters/patient-payments/:patientId/detail
    GET  /encounters/:id/ledger
    POST /encounters/:id/ledger-items
    POST /encounters/:id/payments
    POST /encounters/:id/apply-discount
    PATCH .../ledger-items/:itemId/cancel
  Rule: services post charges; cashier collects money separately.

--- 7.7 Pharmacy POS -----------------------------------------------------------

  Open register session → POS sale (patient can be a pharmacy customer)
  → stock movement → optional sale return / transfer / expense
  Reports: /pharmacy/reports and /pos-reports

--- 7.8 Hospital dashboard -----------------------------------------------------

  GET /hospital-dashboard/summary          (hospital_dashboard.read)
  GET /hospital-dashboard/doctor-summary   (doctor daily view)
  POST /hospital-dashboard/doctor-summary/email

8. AUTH, ROLES, PERMISSIONS
================================================================================

Login is primarily Central Auth, not isolated local passwords:
  - User signs in at www.hisaar360.com
  - Frontend stores token, refresh_token, user, role, roleId, permissions
  - Every API call sends Authorization: Bearer <token>
  - Access token TTL ~10 minutes; AuthService.refreshSession() uses refresh token
  - Change password revokes session; user is sent back to hosted login
  - Single active session per user (new login kills the previous one)

Default hospital role templates (src/modules/roles/hospital-role-templates.js)
upserted per company:

  superAdmin      *  (all hospitals)
  Hospital Admin  full hospital ops (no pharmacy POS keys unless added)
  Doctor          own patients, history, appointments status, prescriptions
  Receptionist    patients, appointments, bills/encounters payments, allotments
  Accountant      bills + full ledger + charge catalog
  Pharmacy        prescriptions.read + POS/inventory/sales/register
  Laboratory      patients + lab tests/orders/verify
  Ward Admin      rooms, allotments, ward.*, history, encounters.read
  Nurse           ward care (no room create/delete, no allotment create)

Laboratory edition templates (narrower):
  superAdmin, Hospital Admin, Laboratory
  Permissions clipped to LABORATORY_EDITION_PERMISSIONS.

Frontend default routes (access-control.ts):
  laboratory edition → /laboratory
  Doctor             → /doctor-dashboard
  Ward Admin / Nurse → /ward/dashboard
  Receptionist       → /appointments
  else first matching permission route, else /settings

Hospital scope (src/common/utils/hospital-scope.js):
  - Non-superAdmin MUST have hospitalId
  - Queries always filter hospitalId
  - Doctor role additionally limited to assigned patients / own appointments

Product edition (src/common/utils/product-edition.js):
  Plan aliases laboratory|lab|lab-only|pathology → LABORATORY
  Auth middleware filters permissions to the edition set.

9. LINKING RULES (IMPORTANT PRODUCT RULES)
================================================================================

  - Clinical data is hospital-scoped. Super admin must send hospitalId
    when creating records; hospital users inherit req.user.hospitalId.
  - Patient is the receivable owner for clinical money (encounter ledger).
  - Lab order always tries to attach an Encounter and a ledger_item
    (and a legacy Bill). Do not remove that dual-write without a migration.
  - Room allotment create opens an admission encounter; discharge posts bed
    charges. Do not discharge without going through those services.
  - Pharmacy stock changes go through InventoryService only (except seed).
  - Products never store current stock; inventory rows + stock_movements do.
  - Doctor login is NOT the same as DoctorProfile, but they are usually linked.
  - Staff-like ward nurses are app Users with role Nurse; they are login users.
  - Wildcard '*' bypasses hospital scope — treat as platform super admin.
  - Laboratory edition must not expose pharmacy/ward/appointment menus.
